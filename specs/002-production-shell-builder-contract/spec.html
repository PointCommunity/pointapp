Specification 002 · Approved September 7, 2026

Production app shell and Builder contract

Prepare PointCommunity/pointapp to become the production Android and Apple application while a separate PointApp Builder eventually authors and publishes content, layout, navigation, and supported element configuration.

Objective

Deliver one branded Point Community Church app shell that is locally testable across Android phones/tablets and iPhone/iPad, store-releasable through an exact-candidate pipeline, and capable of receiving safe configuration updates without a binary release. The app must adapt to its current viewport, remain useful during outages, and reject configuration it cannot safely render.

Confirmed direction

  • PointCommunity/pointapp is the native production source of truth.
  • PointApp Builder is a separate repository and application. It is not built in this scope.
  • The app is a compiled framework plus environment; Builder publishes declarative content and configuration into it.
  • Expo SDK 57, React Native, and strict TypeScript are the accepted foundation.
  • Local Android and Apple testing are required across handset and tablet viewports.
  • Android tablets and iPad receive adaptive compact, medium, and expanded-width layouts from the same component registry.
  • Spectrune's repository skills, one-active-Issue model, exact-tree approvals, and remediation loop are adopted and target-aligned.
  • Point Community Church ships first; multi-organization boundaries remain explicit but white-label operations are deferred.

Actors

  • App user: consumes public and authorized Point content and services.
  • Builder Editor: edits and previews drafts.
  • Builder Publisher: publishes an exact candidate to Staging.
  • Builder Administrator: promotes the exact verified Staging candidate to Production.
  • Native release operator: manages local builds, signing, TestFlight/Play tracks, store submission, rollout, and rollback.
  • Developer/agent: implements and validates one Issue through both target-platform gates.

User scenarios

P1 · First launch with no network

Given a fresh install and no connectivity, when PointApp opens, it renders the bundled Point bootstrap release, identifies its source in diagnostics, and offers no broken or blank primary navigation.

P1 · Activate a Builder release

Given a compatible immutable production release, when the app refreshes its channel pointer, it verifies organization, schema, capabilities, integrity, and URL safety before atomically activating the release and preserving the prior known-good version.

P1 · Reject unsafe or incompatible configuration

Given a malformed, tampered, cross-organization, newer-schema, or unsupported-capability release, when the app evaluates it, it rejects the candidate, retains the current usable release, records a safe diagnostic reason, and does not partially render it.

P1 · Validate one exact native candidate

Given an Issue candidate, when Android and Apple gates run, each installed beta is tied to the same exact source tree and configuration fixture digest, and each target receives its own human checklist and explicit Beta approved - Android or Beta approved - Apple decision.

P1 · Adapt across handset and tablet windows

Given the same accepted release on Android or Apple, when the usable window crosses compact, medium, or expanded width because of device size, rotation, split-screen, fold state, or resizing, the app selects only compiled responsive variants while preserving navigation, content state, focus, and accessibility.

P2 · Roll back configuration without a store release

Given a production content defect, when an Administrator promotes the previous immutable release, compatible apps observe the production pointer change, validate it, and return to the prior experience without downloading executable code.

Functional requirements

  1. PA-001: The repository shall own one cross-platform app shell for Android and Apple with explicit platform adapters.
  2. PA-002: Development, beta, and production builds shall isolate IDs, storage, endpoints, visual identity, credentials, and release history.
  3. PA-003: The app shall ship a complete valid bootstrap release and shall retain a last-known-good remote release.
  4. PA-004: A release envelope shall identify contract/schema version, release, organization, channel, publication time, client/runtime compatibility, required capabilities, canonical digest, and authenticity evidence.
  5. PA-005: The app shall accept only stable component IDs compiled into its registry and reject unsupported capabilities before rendering.
  6. PA-006: Remote configuration shall be declarative data and shall never be evaluated as executable code or define a privileged native bridge.
  7. PA-007: Release validation shall cover schema, organization, compatibility, capability, integrity, authenticity, URL/deep-link policy, and internal referential integrity.
  8. PA-008: Activation shall be atomic. Interrupted or corrupt downloads shall not replace the current usable release.
  9. PA-009: Diagnostics shall expose safe build/release identity and fallback reason without tokens, private member data, or signing material.
  10. PA-010: Builder preview, Staging, Android, and Apple shall consume deterministic fixtures governed by the same contract semantics.
  11. PA-011: Editors shall not publish; Publishers shall stop at Staging; only Administrators shall promote the exact verified Staging release to Production.
  12. PA-012: Native runtime changes shall pass exact-candidate Android and Apple approval before merge and later store release.
  13. PA-013: Content publication and native binary release shall remain separately authorized and auditable.
  14. PA-014: Accessibility shall cover screen readers, focus order, text scaling, contrast, reduced motion, touch targets, safe areas, and applicable hardware/keyboard behavior.
  15. PA-015: Deep links, WebViews, media URLs, push payloads, permissions, and authentication callbacks shall use explicit allowlists and fail-safe behavior.
  16. PA-016: The app shall centrally classify the current usable width as compact below 600 logical pixels, medium from 600 through 839, or expanded at 840 and above, and shall react to live window and text-scale changes.
  17. PA-017: Builder releases may select only registered semantic layout variants and bounded tokens; arbitrary breakpoints, absolute device assumptions, native style objects, and executable layout rules are prohibited.

Project structure and style

The planned structure is defined in AGENTS.md §5. TypeScript uses strict types, stable domain names, exhaustive discriminated unions for component definitions, pure validation/selection functions, thin native views, no unchecked type assertions at trust boundaries, and comments that explain constraints rather than restating code.

Testing strategy

  • Unit: canonicalization, validation, capability selection, URL policy, viewport classification, cache decision, fallback, and migration logic.
  • Contract: valid and hostile Builder release fixtures; registered layout variants; backward/forward compatibility; deterministic digest; app/preview agreement.
  • Integration: fetch, conditional refresh, interruption, atomic storage, offline launch, rollback, diagnostics, and state preservation while the viewport changes class.
  • Native flow: navigation/render/accessibility at compact, medium, and expanded widths on Android phone/tablet and iPhone/iPad simulators or emulators for every candidate.
  • Real device: before store production on current Android phone/tablet and iPhone/iPad hardware for applicable permissions, notifications, deep links, authentication hand-off, background media, casting, performance, resizing, and accessibility.
  • Security: dependencies, source, configuration trust boundary, native manifests/entitlements, secrets, packages, and manual review.

Success criteria

  • SC-001: One accepted scaffold starts from a clean checkout and launches locally on both an Android Emulator and iOS Simulator.
  • SC-002: The same valid fixture release renders the agreed first navigation/page flow on both targets.
  • SC-003: Every invalid fixture class is rejected without replacing the current usable release.
  • SC-004: A fresh offline install renders the bundled bootstrap, and a warm offline launch renders last-known-good.
  • SC-005: Configuration rollback selects the prior immutable release in under five minutes without a native rebuild.
  • SC-006: Development, beta, and production storage/endpoints are mechanically isolated.
  • SC-007: The exact latest candidate completes both native target approvals and all automated gates before merge.
  • SC-008: No remote release can invoke an unregistered capability or executable behavior.
  • SC-009: One release preserves content, navigation, focus, and usable composition while transitioning among compact, medium, and expanded widths on Android and Apple.

Decision record

D1 · Resolved: React Native with Expo SDK 57 and strict TypeScript is accepted; use development builds and local native tooling.

D2 · Resolved: Production uses org.pointcommunity.pointapp; beta and development add .beta and .dev. Visible names are PointApp, PointApp Beta, and PointApp Dev. Organization accounts own identifiers and signing assets; named custodians are release evidence, not source.

D3 · Resolved and expanded: Support Android 7+ and iOS/iPadOS 16.4+ across phones and tablets. Validate compact, medium, and expanded current-window classes on Android and Apple, including Android tablet and iPad resizing checks. See the environment matrix and ADR 0003.

D4: Decide the future Builder publication endpoint/storage and authenticity-key custody before the contract implementation reaches remote fetch.
