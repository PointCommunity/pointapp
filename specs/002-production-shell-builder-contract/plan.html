Implementation plan: production shell and Builder contract

This replaces the earlier assumption that parity, Builder, backend, and mobile clients should advance as one large build. Delivery now starts with a small production shell and one contract slice, then expands domain by domain.

Dependency path

Governance→Decisions + toolchains→Native shell→Contract v1→Fetch/cache/recovery→First renderer slice→Builder integration→Store readiness

Architecture decisions

  • Accepted: app and Builder are separate products joined by an immutable, declarative, data-only contract.
  • Accepted: native binary and configuration publication use independent release planes and authority.
  • Accepted: the app ships bootstrap and last-known-good recovery and rejects unsupported releases before render.
  • Accepted: Expo SDK 57, React Native, and TypeScript, using development builds and local Xcode/Android tooling.
  • Accepted: isolated org.pointcommunity.pointapp production, beta, and development identities; Android 7+; iOS/iPadOS 16.4+.
  • Accepted: one current-window classifier drives compact, medium, and expanded compositions across Android phone/tablet and iPhone/iPad; Builder selects only compiled semantic variants.
  • Deferred: hosting/CDN, signature format/key custody, named signing custodians, and the first complete feature-domain roadmap.

Phase 0 · Repository governance

Prepared locally in this pass.

  • Adopt tailored Spectrune workflow skills and shared design packages.
  • Establish one-active-Issue, exact-candidate, and Android/Apple approval rules.
  • Record the Builder boundary, revised spec, plan, tasks, research, ADRs, changelog, CI, and foundation validation.
  • Do not commit, push, create a Project/Issue, scaffold the app, or change Builder.

Phase 1 · Resolve decisions and enable both local targets

  1. Human reviews the specification and ADR 0002.
  2. Lock app IDs, visible channel identities, first OS/device matrix, and account/signing ownership without committing secrets.
  3. Install and verify an iOS Simulator runtime/device plus Android Studio SDK/emulator, JDK, and optional Watchman.
  4. Create the dedicated PointApp organization Project only with explicit authorization; configure controlled fields and verify the one-active-Issue invariant.

Checkpoint: both local target toolchains pass a minimal preflight and all material scaffold decisions are accepted.

Phase 2 · Scaffold one production-capable shell

  1. Create the accepted current Expo/React Native TypeScript application using development builds.
  2. Define isolated development, beta, and production identities/endpoints/storage.
  3. Add stable commands for format, type, lint, unit, contract, integration, iOS, Android, and no-submit beta builds.
  4. Add CI that runs platform-neutral gates and validates generated native configuration.

Checkpoint: one clean source tree launches the bundled placeholder/bootstrap route in iOS Simulator and Android Emulator; no Builder/network dependency exists.

Phase 3 · Freeze and prove configuration contract v1

  1. Write machine-readable release-envelope and component-definition schemas plus valid/hostile fixtures.
  2. Implement deterministic canonicalization, digest/authenticity interface, compatibility and capability negotiation, organization isolation, URL policy, and actionable safe errors.
  3. Generate or share consumer types without making Builder source a runtime dependency.
  4. Publish the frozen v1 contract package/artifact for the Builder team after exact review.

Checkpoint: app and independent contract tooling agree on every fixture; remote executable behavior is mechanically impossible.

Phase 4 · Fetch, cache, and recover

  1. Add build-channel bootstrap endpoint selection and conditional channel-pointer fetch.
  2. Download and validate immutable releases before atomic persistence.
  3. Implement bundled bootstrap, last-known-good, corrupt/interrupted cache recovery, offline launch, rollback, and safe diagnostics.
  4. Test slow, unavailable, replayed, invalid, cross-organization, and incompatible responses.

Checkpoint: the app never loses a usable configuration because a new candidate is bad or connectivity fails.

Phase 5 · Deliver the first adaptive Builder-driven experience

  1. Implement the central compact/medium/expanded viewport classifier and responsive primitives.
  2. Implement the smallest compiled registry: app theme tokens, tab/navigation shell, page, stack/section, text, image, button/link, and media-card entry only as approved.
  3. Render one deterministic five-tab-or-smaller fixture end to end at all three size classes on Android phone/tablet and iPhone/iPad.
  4. Cover safe areas, text scaling, screen readers, focus/order, orientation, live resizing, state preservation, reduced motion, touch targets, deep-link fallback, loading, empty, error, and offline states.
  5. Capture target- and viewport-specific parity evidence against the same release digest.

Checkpoint: both native platforms adapt and navigate the same accepted contract release across handset and tablet windows, with documented intentional platform differences only.

Phase 6 · Integrate the future PointApp Builder

  1. The Builder imports the frozen contract and produces the exact fixtures the app already accepts.
  2. Implement draft/preview, Staging publication, Administrator exact-candidate Production promotion, audit, concurrency protection, and rollback in the Builder repository.
  3. PointApp beta consumes Staging; production app consumes Production. Verify propagation and last-known-good behavior.

Checkpoint: a Builder-authored candidate reaches both native apps through the same data contract without a binary rebuild. Builder implementation is explicitly outside the current task.

Phase 7 · Native prerelease and store readiness

  1. Complete real-device tests for applicable permissions, notifications, deep links, auth hand-off, media/background behavior, casting, and performance.
  2. Produce signed Android App Bundle and Apple archive/TestFlight candidates under controlled credentials.
  3. Run Play internal/closed testing, pre-launch reports, TestFlight validation, accessibility/privacy declarations, review accounts, store metadata, monitoring, staged rollout, and rollback rehearsal.
  4. Require explicit authorization for exact store submissions and production rollout.

Parallel work boundary

The user's Builder repository setup may proceed independently through repository creation and governance. Contract implementation should not diverge in parallel: freeze PointApp contract v1 and fixtures first, then hand the exact reviewed artifact to Builder. Native shell/toolchain work and Builder repository administration can proceed concurrently because they do not share a schema yet.

Plan approval gate

Application implementation starts only after the human reviews the specification, resolves D1–D3, and confirms the first implementation Issue. D4 may remain open until remote fetch is scheduled, but contract v1 must leave an explicit authenticity interface.
