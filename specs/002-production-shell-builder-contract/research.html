Research: production shell and Builder contract

Evidence reviewed September 7, 2026. Live products, policies, and local tooling can change; refresh before implementation or release.

Repository evidence

  • Authenticated GitHub inspection confirmed the private repository PointCommunity/pointapp with description “Independent extensible ministry app builder, content platform, and mobile application.” It currently has no default branch, Issues, pull requests, or dedicated organization Project.
  • The local checkout contains the earlier parity specification and a public Subsplash support index with 15 collections and 444 unique article records. That catalog remains an index with zero fully reviewed articles, not a complete requirements authority.
  • Spectrune provides nine project workflow skills, five shared design skills, a one-active-Issue pipeline, exact-candidate beta approvals, and paired native validation. PointApp adopts the discipline while replacing Windows/macOS desktop hosts with Android/Apple target gates.
  • PointSite Builder establishes a relevant role boundary: Publisher to Staging; Administrator promotes the exact Staging candidate to Production. PointApp applies this to configuration publication, not native app deployment.

Store policy constraints

EvidencePointApp implication
Apple App Review Guidelines 2.5.2 restrict downloaded or executed code that introduces or changes app functionality.Builder publishes declarative data for compiled capabilities. No downloaded JSX, JavaScript modules, native bridge definitions, or arbitrary executable behavior.
Apple Guideline 4.2 requires useful, app-like functionality and addresses commercialized template services.PointApp must deliver a distinct Point Community Church experience with real native utility. The church/provider submits its own branded app; the long-term multi-tenant model requires a separate policy review.
Google Play Device and Network Abuse policy restricts self-updates and executable code outside Play.Configuration cannot modify the installed executable. Native changes ship through Google Play.
Android App Bundle test guidance describes internal, closed, and open testing plus Play pre-launch reports.Local Android validation remains mandatory; Play internal testing and pre-launch reports become later distribution evidence, not substitutes for exact-candidate approval.

Local environment snapshot

  • Available: Node 22.23.2, npm 10.9.8, Xcode 26.6.
  • Not observed as usable: iOS Simulator devices/runtimes, Android adb, Android emulator, Java runtime, Watchman.
  • The environment is sufficient for repository planning and Node-based foundation checks, but not for the requested dual-platform native gate.

Resulting architectural decisions

  1. Use separate native and configuration release planes.
  2. Make all Builder output immutable, declarative, versioned, capability-bounded, organization-scoped, integrity-checked data.
  3. Ship bundled bootstrap plus last-known-good recovery.
  4. Validate the same release fixtures in Builder preview, Android, and Apple.
  5. Keep Expo as a proposed foundation until the human approves the ADR and a two-target proof succeeds.
