ADR 0003: Use adaptive viewport classes across phones and tablets

Accepted · September 7, 2026

Context

PointApp must support Android phones, Android tablets, iPhone, and iPad. Hardware labels are insufficient because rotation, Android multi-window, iPad split view, foldables, and desktop-style windowing can give the same device several usable widths during one session.

Decision

Drive layout from the current usable application window and centralize three width classes: compact below 600 logical pixels, medium from 600 through 839, and expanded at 840 or above. Recompute class when window dimensions change. Height, safe-area insets, text scale, keyboard, and accessibility settings remain independent inputs when a component needs them.

ClassWidthTypical presentation
Compact< 600Single-pane handset or narrow split-window flow.
Medium600–839Tablet portrait, large foldable, or medium window with wider spacing and optional supporting content.
Expanded≥ 840Tablet landscape or large window where approved multi-pane composition may appear.

Builder boundary

The compiled registry owns breakpoints, responsive primitives, safe fallbacks, and accessibility behavior. Builder configuration may choose only registered semantic variants such as single-column, supporting-pane, or auto, with schema-bounded tokens. Unknown variants are rejected before render. Builder cannot send arbitrary React Native styles, absolute screen coordinates, device-model branches, breakpoint values, or executable layout rules.

Consequences

  • Every renderer fixture is tested at compact, medium, and expanded widths on both Android and Apple.
  • Android tablet and iPad simulator coverage are explicit native gates alongside handset coverage.
  • Rotation and live resizing must preserve navigation, focus, content state, and accessibility.
  • Layouts expand or reorganize; they do not merely scale handset UI or stretch text to fill space.
  • This record supersedes ADR 0002 only where ADR 0002 described iPad as compatibility without a tablet layout requirement. The Expo framework decision remains accepted.

Alternatives considered

  • Device-type checks: rejected because one device can occupy compact, medium, or expanded windows.
  • Separate tablet application: rejected because it duplicates product, contract, release, and test paths.
  • Builder-defined CSS-like rules: rejected because native behavior, safety, accessibility, and compatibility must remain compiled and testable.
  • Two classes only: rejected because portrait tablets and landscape tablets often need meaningfully different composition while still sharing components.

Official evidence

  • Android window size classes
  • React Native useWindowDimensions
