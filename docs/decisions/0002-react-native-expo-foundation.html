ADR 0002: Use React Native with Expo for the first PointApp shell

Accepted · September 7, 2026

Context

PointApp needs one TypeScript product for Android and Apple, rapid local simulator/emulator work, development builds that can include native modules, and a future Builder contract that can share schemas and fixtures with a TypeScript web application.

Decision

Start with Expo SDK 57, React Native, and TypeScript, using development builds rather than Expo Go for production-grade work. Pin compatible dependency versions and upgrade through explicit reviewed changes. Keep native projects reproducible with Continuous Native Generation and build both targets locally through Xcode and Android Studio tooling. Use Expo runtime compatibility metadata only for native/JavaScript update safety; Builder content remains a separate data API and never rides as executable code.

Why this leads

  • Expo is a React Native framework for Android and iOS and officially recommends development builds for production projects.
  • Official local-build guidance supports npx expo run:ios and npx expo run:android with Xcode and Android Studio.
  • TypeScript contracts can be shared or generated consistently between the app and future Builder.
  • The project retains access to native modules and store-native packaging when required.

Alternatives

  • Bare React Native: maximum direct control, but more native setup and maintenance before product value.
  • Separate Swift and Kotlin apps: strongest platform specialization, but duplicates configuration, rendering, and product logic.
  • Flutter: viable cross-platform option, but adds Dart and reduces direct sharing with a likely TypeScript Builder.

Consequences and required proof

  • Expo SDK 57 sets the initial compatibility floor at Android 7+ and iOS/iPadOS 16.4+.
  • Development, beta, and production variants require distinct identifiers and storage.
  • A minimal development build must run on an iOS Simulator and Android Emulator from this Mac before the scaffold can pass its native gate.
  • iPad receives compatibility coverage in release one, including installation, launch, rotation/resizing, accessibility, and core-flow checks; a tablet-specific layout is not required.
  • A deterministic local fixture must render compatibly on Android, iPhone, and iPad before the first renderer slice is accepted.
  • If a required capability outgrows Expo's managed configuration, use config plugins or generated native projects before considering a framework replacement.
