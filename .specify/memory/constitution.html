PointApp project constitution

Version 2.0.0 · Ratified August 31, 2026 · Amended September 7, 2026

1. Independent implementation

PointApp may pursue functional parity using public behavior, authorized observation, and independently designed code. It must not copy proprietary source code, protected branding, private APIs, or copyrighted documentation. Every externally derived requirement must retain a source link and evidence status.

2. Specification and traceability first

No product capability enters implementation without a testable requirement, acceptance scenario, owning product domain, and roadmap phase. Research findings, specifications, plans, tasks, and validation evidence must remain synchronized.

3. Security, privacy, and tenant isolation

Identity, permissions, sensitive member data, messaging, payments, and administrative actions are security-critical. Least privilege, encryption, auditability, abuse controls, data retention rules, and organization isolation are mandatory design gates.

4. Separate products, one versioned contract

PointCommunity/pointapp owns the production Android and Apple shell. PointApp Builder is a separate product and repository. They meet only through a versioned, immutable, declarative data contract. A published configuration must render predictably in preview and on supported devices. Accessibility, offline and poor-network behavior, backward-compatible schemas, exact-candidate publication, rollback, and app-store compliance are release requirements.

5. Extensible parity

Parity is a roadmap target, not permission to reproduce another product's internal architecture. Domain boundaries, versioned contracts, feature flags, and replaceable integrations must preserve room for PointApp-specific capabilities.

6. Evidence-based validation

Critical user journeys require automated tests and observable acceptance evidence. Core business logic targets at least 80% line coverage, but coverage never substitutes for integration, security, migration, accessibility, and device validation.

7. Human-readable artifacts

All documents and diagrams intended for people must be delivered as dark-mode HTML. Machine-readable JSON, source code, test fixtures, and generated build metadata are exempt.

8. Independent release planes

Native binaries and app configuration use different gates and authorities. Android and Apple runtime changes require separate exact-candidate native approval. Builder configuration is data-only, moves through Staging before Administrator-authorized Production promotion, and must never inject executable behavior or native capabilities.

Governance

  • Architecture or scope changes that alter a product boundary require an explicit decision record.
  • Critical, high, and medium consistency findings must be remediated before implementation.
  • Commits, pushes, Project and Issue creation, releases, deployments, production configuration publication, and store submissions require the applicable explicit authorization.
  • Constitution amendments require stakeholder discussion, a version change, rationale, and date.
